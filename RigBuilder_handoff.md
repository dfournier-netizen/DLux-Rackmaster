## 1. What this is

**DLux Rackmaster** is a single self-contained HTML file that does three jobs for touring/mobile AV production: physical rack elevation building, port-level signal routing, and lighting power/DMX planning. It's inspired by Vectorworks ConnectCAD but scoped for one person (the user, Dom, a production/AV professional) working solo, fast, and offline — at a venue, in a truck, wherever — with zero setup.

It runs by double-clicking the `.html` file. No install, no server, no build step, no network calls, ever. Everything — HTML, CSS, and JavaScript for the whole app, plus two vendored third-party libraries — lives in that one file.

**Five top-level views:** Library (device templates), Racks (physical rack elevation builder), Routing (port-level signal flow, single-rack scoped), Rig (system-level view — all racks + edge devices + inter-rack cabling), Lighting (a merged-in lighting-power/DMX-patch subsystem called RIGPOWER), plus a Settings view (units, stock lengths).

## 2. Non-negotiable design principles

These have held across the whole project history and should not be silently abandoned by a future session without the user explicitly signing off — several were tested and reaffirmed under real pressure this session, not just stated once and forgotten.

- **Zero network dependency.** No fetch calls, no CDNs at runtime, no external services. This was stress-tested directly: the user asked about pulling fixture data from an online GDTF Share library, a live in-browser integration was prototyped and hit a real CORS wall (browsers block cross-origin credentialed requests from a `file://`-opened page, and there's no evidence GDTF Share's API is built for arbitrary browser JS at all — see §9 for the full investigation). The resolution was explicitly to *not* compromise this principle: local `.gdtf` file import (already existed — see §9) was kept as the answer instead of adding a server/proxy or hosting the app online.
- **Single file.** Not a philosophical preference — it's what makes "email yourself the file, double-click it anywhere" work. JSZip and Three.js are vendored inline (not CDN-loaded) for exactly this reason.
- **Runs fully local, per-file storage.** `localStorage` autosave is keyed by file path, so a new timestamped file starts fresh — carrying work forward is an explicit **Export Project → Import Project** (`.dlux.json`) action, never automatic. This is a known-and-accepted quirk, not a bug to "fix" by switching storage strategy.
- **Accessibility as an ongoing constraint, not a one-time pass.** Minimalist, high-contrast UI; dyslexia-friendly type (Verdana stack, generous letter/line spacing); everything labelable and color-codable. When a contrast bug was found this session (leg-graph colors nearly invisible on light theme), it was treated as a real bug worth root-causing properly (WCAG contrast math), not a cosmetic nice-to-have.
- **User terminology preferences, treated as fixed vocabulary, not style suggestions:** say **"ports,"** never "jacks" (in UI copy/labels — the underlying data field is still named `jacks[]` internally, see §5, but nothing user-facing should say "jack"). Say **"BiDi,"** never "Bi," for bidirectional port direction. Same rule applied to the new power-circuits copy this session: **"circuit," "draw," "W"** are the vocabulary — no synonyms substituted.

## 3. Architecture

**No frameworks, no build step.** Vanilla JS throughout, `"use strict"`.

The HTML file is composed of five `<script>` tags plus CSS:
- **script0** — the main Rackmaster app (Library/Racks/Routing/Rig/Settings, ~211K characters at last count).
- **script1** — JSZip 3.10.1, vendored verbatim.
- **script2** — Three.js r128, vendored verbatim (powers the Lighting module's 3D plot).
- **script3** — RIGPOWER, the lighting module (~98K characters), shadow-DOM isolated (see below).
- **script4** — a small (~450 char) merge/glue script wiring RIGPOWER's exposed API into the main app's state and render cycle.
- A main `<style>` block for Rackmaster's own theming, **plus a separate `<style>` block inside `<template id="rpTpl">`** that only applies within RIGPOWER's shadow root — these are two distinct stylesheets and edits must go in the right one.

**Shadow-DOM isolation for RIGPOWER.** RIGPOWER was originally a separate standalone app that got merged in (v6.0). Rather than rewrite it to share Rackmaster's DOM/CSS namespace, its markup and styles live inside `<template id="rpTpl">`, hosted in a shadow root attached to `<div id="rpRoot">`. This means zero ID/class/selector collisions with Rackmaster by construction — a deliberate integration shortcut that's held up well and should probably stay, rather than being "cleaned up" into a full merge, unless there's a concrete reason to. RIGPOWER's internals are wrapped in an IIFE and expose a narrow API on `window.RP`:
```
window.RP = { getState, setState, onShow, host, refresh, buildRun, computeAutoCable, getStock }
```
`RP.getState()` returns `{ state, stockLengths }` — note the extra `.state` nesting; a common mistake is to forget it and expect `getState()` to return the fixtures/devices directly.

**Cross-shadow-boundary theming.** CSS custom properties inherit through shadow boundaries by design, so Rackmaster exposes `--rm-*` aliases on its outer `:root` / `[data-theme="dark"]` blocks, and RIGPOWER's shadow `:host{}` block reads them with fallbacks, e.g. `--legX:var(--rm-legx,#4aa3e0)`. Any new themed value that needs to cross into RIGPOWER's shadow DOM should follow this exact pattern — define it outer-side as `--rm-<name>`, reference it shadow-side as `var(--rm-<name>, <fallback>)`. (The v6.6 power-circuit load bars deliberately did **not** need a new bridge — they live entirely on the Rackmaster side and reuse the already-theme-aware `--ok`/`--amber`/`--danger` vars directly.)

**State model.** One global object `S`:
```
S = { meta, library, racks, edges, connections, ui, lighting }
S.lighting = { state, stockLengths }   // bridges into RIGPOWER's internal state
```
Mutating state and wanting it saved + re-rendered: call `commit()` (= `save()` to localStorage + full `render()`). For non-structural edits that don't need a re-render, call `save()` alone.

**Render pattern — the single most important gotcha in this codebase.** `render()` fully wipes `#view` (`v.innerHTML = ""`) and rebuilds everything from state on every commit. There is no virtual DOM, no diffing. This is fine for click-driven UI, but it is a recurring, repeat-offender source of bugs: **if a render function is called synchronously inside an `oninput` handler, the DOM node the user is typing into gets destroyed and recreated on every keystroke, which yanks keyboard focus after one character.** This exact bug was found and fixed twice in this project's history (Fixtures tab's Watts field, v6.5's Library/cable search boxes) — the fix pattern is always the same: `oninput` should only mutate the in-memory state object (no render call), and the actual re-render should happen on `onchange` (fires on blur/Enter, once the value has settled). Before adding any new text/number input anywhere in the app, check whether its `oninput` handler calls a render function, and if so, split it this way preemptively. v6.6's Power draw (W) fields (both Device Inspector surfaces) follow this split exactly and are a good reference example.

**Sync bridge.** A debounced (300ms, capture-phase) listener on `RP.host.shadowRoot` watches `input`/`click`/`keyup`/`change` and calls `S.lighting = RP.getState(); save();` — this keeps the outer app's autosave aware of RIGPOWER-side edits without RIGPOWER needing to know Rackmaster exists.

**Migration.** `migrate()` runs on every load/import and backfills any state fields added in later versions (also heals old bugs, remaps renamed port types, backfills library depths). Any new persisted state field added to the data model needs a corresponding default added here, or old project files will break on import. v6.6 additionally introduced a **dangling-reference healing** pattern in `migrate()` (a device's `circuit` field pointing at a since-deleted `rack.circuits[]` entry gets reset to `null`) — worth reusing if a future feature introduces another cross-referencing id field.

## 4. Domain rules (the load-bearing math)

- **Placement:** `canPlace(rack, pos, u, ignoreId, w, side, probe)`. Checks vertical overlap, then a lateral check (half-width units can share a row on opposite sides), then a **depth check** via `depthRange(dev, rack)`, which returns the occupied span in inches including a **2.5" connector/cable-room allowance** (front mounts grow rearward, rear mounts grow inward, inside mounts sit at `insideOff`, auto-centered when `inOff == null`). Front/rear/inside mounts can legally stack in the same U row as long as their depth spans don't intersect. `findBlocker`/`blockMsg` identify the specific colliding unit for error toasts. v6.6's touch-drag reposition gesture (§8) reuses `canPlace()`/`blockMsg()` verbatim for live drop validation — no new placement math was needed.
- **Face visibility:** front view shows front-mounted gear; rear view shows rear-mounted gear plus any front-mounted gear deep enough to reach within 3" of the rear; inside-mounted units show dashed on both faces with an `IN` badge. Left/Right side views (`sideSVG`) render the depth cross-section with the cable-room strip shaded.
- **Cable length default:** `12" base + 4" per connector (x2) + 3.5"/U vertical + detour past deeper gear in the path + 6" lateral + 10" strain relief`; rack-to-rack runs add 24" up-and-over; edge runs use base + allowances. Editable per-cable; an "Auto" button recalculates.
- **Library depths:** `SEED_DEPTHS` maps common template names to typical chassis depths (Blank Panel 0.5" ... UPS 19", Media Server 20"). Unrecognized gear falls back to a `Depth (in)` field or a flat 18" default.
- **Lighting power model (GDTF-derived, see §9):** per-mode wattage is computed by walking the DMX mode's referenced geometry tree and summing every `<Beam PowerConsumption="...">` found (resolving `GeometryReference` indirection), not read from a single flat property — this handles multi-emitter fixtures correctly. Per-mode DMX footprint (channel count) is the max `Offset` value found across that mode's `<DMXChannel>` elements, falling back to a simple element count if no offsets are present.
- **Rack power circuits/load (v6.6, new):** `circuitLoad(rack, circuitId)` sums `draw` (watts) across every device in the rack assigned to that circuit; `circuitCapacityW(c)` = `amps × volts`; `circuitPct` = load/capacity; `circuitLoadClass(pct)` returns `"ok"` under 80%, `"warn"` at ≥80%, `"over"` strictly above 100%. This is deliberately independent of RIGPOWER's own (pre-existing) lighting circuit/phase-load math — rack power circuits are a Rackmaster-side-only concept, scoped to devices physically in a rack, not lighting fixtures/multicables.
- **Orthogonal wire routing (v6.6, tidy bus lanes as of v6.6.1, node-aware as of v6.6.2):** `wirePathOrthogonal(a, b, connId, laneX)` builds an axis-aligned H/V/H route between the same port-exit stubs curved mode uses, with rounded ~6px corners (`roundedPolylinePath()`, quadratic-Bézier corners on an otherwise-straight polyline). Parallel cables sharing a corridor no longer get a per-id hash jitter; `drawWires()` runs a global `assignWireLanes()` pass each redraw that buckets same-corridor cables (~24px band), sorts them deterministically (dest y, then source y, then id), and spaces them evenly (~14px) centered on the corridor -- a tidy sorted bus, not random-looking offsets. As of v6.6.2, orthogonal mode always avoids device node bodies (no toggle -- curved mode untouched): obstacles are the live rendered rects of every visible `.node`/`.rack-node` (`collectNodeObstacles()`, inflated ~10px), `pickCorridorX()` shifts a blocked vertical corridor to the nearest clear x, `routeHorizontalAvoiding()` detours a blocked horizontal run over/under the shorter side (bounded ~4 detours/cable, graceful straight-line fallback if unroutable), and lane spacing compresses to fit a narrow clear gap rather than pushing a cable back into an obstacle. See §8 for the full writeup. **v6.12.1** adds a Y-LANE pass on top: for cable ends that exit down/up (BiDi ports, which pin their horizontal leg to a shared node-edge y that an x-corridor offset can't separate), `assignWireStubLanes()`/`buildWireStubEnds()`/`wireStubBandKey()` stagger that end's **stub length** (`STUB`+laneIndex*`WIRE_LANE_GAP`, grow-only, down/up ends grouped independently) so the legs fan 28px apart; `wireStubPts`/`wirePathOrthogonal`/`wirePath` gained optional per-end stub-length args (default `STUB`), and an end alone in its band keeps base `STUB` so non-bunched cables stay byte-identical. **v6.12.2** adds render-only per-bus shade variation: `assignWireShades()`/`shadeHexLightness()` step the LIGHTNESS (hue+sat preserved, ~+/-6pt, clamped) of same-colour cables sharing an x-corridor bucket so they're individually distinguishable -- never mutates `c.color`, applied only to the emitted `stroke`.

## 5. Data model (key shapes)

```
S.racks[]        { id, name, sizeU, depth /*in, default 20*/, color, notes, devices[],
                   circuits[] /*v6.6 -- { id, name, amps /*breaker, default 20*/, volts /*default 120*/ }*/ }

device instance  { id, tplId, name, cat, u, w:"full"|"half", side:"L"|"R",
                   mount:"front"|"rear"|"inside", depth /*in|null*/, inOff /*in|null=auto-center*/,
                   pos /*bottom U, 1-based*/, color, isContainer, contents[{id,name,qty}],
                   ports[], fields[{id,key,value}], img, imgRear, notes, rx, ry /*routing canvas*/,
                   hideInRouting /*null=auto|true|false*/, pushProtect /*bool*/,
                   draw /*v6.6 -- watts, null=unknown*/, circuit /*v6.6 -- circuit id within the parent rack, or null=unassigned*/ }
                   // library templates (S.library[]) carry the same "draw" field (watts, null=unknown);
                   // "circuit" is instance-only (assignment is rack-scoped, templates aren't placed in a rack).

port group       { id, name, type, dir:"in"|"out"|"bi", count, face:"front"|"rear", color?,
                   jacks[ {label, fields[]} ] /*per-jack overrides, index-aligned with count*/ }
                   // Note: internal field name is "jacks" even though UI copy always says "ports" -- see §2.

S.edges[]        device instances without pos/rack (consoles, WAPs, antennas -- anything not rack-mounted)
                 // edge devices carry "draw" too (no parent rack -> "circuit" stays null, no UI control for it)
S.connections[]  { id, a:{dev,g,i}, b:{dev,g,i}, label, color, type, len /*inches*/, notes, adapter /*free text*/ }
S.library[]      templates: device shape minus pos/rx/ry, plus cat and draw; containers may carry default contents
S.ui             view state: theme, face, filters, collapsed sections, floating panel geometry
                 (panels/panelHidden), zoomRack/zoomRoute, rigCollapsed, jackEd, selections,
                 routingRackOnly /*single-rack lock, v6.4*/,
                 wireStyle /*v6.6; v6.10.1 -- curved REMOVED, migrate() pins this to "orthogonal";
                 field kept only so old exports round-trip*/,
                 toolMode /*v6.8 -- Routing/Rig canvas tool mode, "select"|"pan", default "select",
                 self-healing in migrate() against any other stored value*/,
                 minimap /*v6.9 -- corner minimap on/off, bool, default true, migrate()-backfilled*/,
                 wireLabels /*v6.10 -- always-visible cable labels on Routing/Rig, bool, default true,
                 migrate()-backfilled; label text falls back to cable type*/,
                 reportSections /*v6.11 -- 12 bool keys gating Rack Guide sections, all default true;
                 backfilled via Object.assign(reportSectionDefaults(), stored) -- add future keys to
                 REPORT_SECTION_DEFS only*/
                 theme is now "light" | "dark" | "evergreen" (v6.10); migrate() heals unknown values to "light"*/

S.lighting.state.fixtures[]   { id, name, watts, mode, count, footprint /*DMX channel count*/, manual /*bool*/, _profile }
S.lighting.state.devices[]    lighting-side devices (distros, DMX nodes/splitters, or library-linked "gear")
```

`MSEL` (`{devs[], conns[], ports[]}`) is a runtime-only (not persisted) multi-select structure shared across Racks/Routing/Rig; `devs[]` holds either a device-instance id or a `"rack:<id>"` key for a collapsed Rig rack container.

## 6. Naming & versioning conventions

- **Build filenames (since 2026-10-19):** `DLux_Rackmaster_YYYY-MM-DD_HHMMSS.html` (America/New_York), e.g. `DLux_Rackmaster_2026-07-22_145918.html`, so names sort by date. Older builds use `DLux Rackmaster HHMMAM/PM MMDDYY.html`; the suite's newest-build defaults accept both. **Every meaningful change produces a brand-new timestamped file -- never overwrite an existing one.** The newest timestamp is always the current build.
- **Git and releases (since 2026-10-19):** the repo (`DLux Rackmaster/`, origin `dfournier-netizen/DLux-Rackmaster`) holds the current build, `base.html` (= `0137PM 072126`, pre-v6.12.1) and `base_A.html` (= `0235PM 072226`, pre-v6.12.2) as the reference builds the byte-identity suites diff against, `test_suite_v6.10/`, and these two docs. Older builds stay out of git. Pushing a `v*` tag runs the suite and publishes the newest build as `DLux-Rackmaster-<tag>.html` on a GitHub Release (`.github/workflows/release.yml`).
- **Show data stays off git:** `LX Network racks.dlux.json` and `test_suite_v6.10/fixture_rackguide_allracks_real.html` are gitignored. `test_wire_shade_variation.js` and `test_ylane_separation.js` need that JSON inside `test_suite_v6.10/`, so they run locally only; CI skips them, and `test_report_scoped.js` skips its real-project guard when the JSON is absent.
- **Live clock, not a remembered one:** the timestamp must come from an actual `date` read taken immediately before the file is written, not a time computed earlier in the session. This bit the project once already (a build was named `0227PM` but actually saved at 5:28 PM, because the name was generated hours before the save at the end of a long batched session) -- always re-check the clock right before writing.
- **Checkpoint cadence:** cut a new timestamped file after each meaningful chunk of work lands, not just once at the very end of a session. A single big multi-hour session with only one final save (v6.3's original approach) leaves no intermediate fallback point if something goes wrong mid-session; several small checkpoints (v6.0-v6.2, v6.4's four intermediate saves, v6.6's two) is the pattern to follow. A same-day, tightly-scoped bugfix pair can reasonably ship as one checkpoint (v6.4.1 did) -- use judgment, but default toward more checkpoints, not fewer.
- **Version numbers:** major bumps (v6.0, v6.1, v6.2...) per session or per significant feature batch; a `.1` suffix (v6.4.1) for a same-day, smaller, tightly-scoped follow-up that doesn't warrant a full version bump.
- **Test suite folders:** named to match the version they were introduced for (`test_suite_v6.10/` is current, superseding `test_suite_v6.9/`), containing one `.js` file per feature area (not one giant file), plus a `run_all.js` that auto-detects the newest `DLux Rackmaster *.html` in the parent folder so it keeps working against future builds without path edits. Every test file accepts an optional `process.argv[2]` path override, matching this convention -- new test files should too.
- **Project docs, two of them, different purposes:** `DLux Rackmaster — Project Notes.md` is the durable, chronological changelog/reference (architecture, data model, one section per shipped version, backlog) -- append to it, don't replace sections. This file (`RigBuilder_handoff.md`) is the standalone "pick this up cold" brief -- it should stay current with the *present* state, not accumulate full version-by-version history (that's what Project Notes is for).

## 7. Testing conventions

- jsdom **29.1.1** (pinned: under jsdom 30, `test_undo_redo.js`'s RIGPOWER shadow-root focus check fails) (`JSDOM` with `runScripts:"dangerously"`), one test file per feature area, `assert(condition, label)` pattern with a running pass/fail count, `process.exit(fail ? 1 : 0)`.
- **Use realistic event subclasses** -- `MouseEvent`/`PointerEvent`/`KeyboardEvent`, not generic `Event` -- when the app code reads `clientX`/`clientY`/`key`. jsdom's `PointerEvent` constructor works fine for touch-gesture tests (`pointerType: "touch"`) -- confirmed working in v6.6's `test_touch_reposition.js`.
- **Stub `<dialog>`:** jsdom doesn't implement `showModal`/`close`. Every test touching a `<dialog>` needs:
  ```js
  win.HTMLDialogElement.prototype.showModal = function(){ this.open = true; };
  win.HTMLDialogElement.prototype.close = function(){ this.open = false; };
  ```
- **Known, accepted jsdom gaps -- verify these by hand in a real browser instead of fighting jsdom:** the 3D plot tab (Three.js/WebGL); MVR and GDTF file drag-drop import (confirmed this session -- `JSZip.generateAsync()`/`loadAsync()` hang indefinitely in jsdom, apparently a Blob-internals gap, not an app bug -- if you need to test GDTF/MVR *parsing logic* specifically, bypass JSZip in the test and hand-construct a DOM via `win.DOMParser` directly against the parsing functions, the way `test_gdtf_parse_logic.js` does); real touch-device feel (tap latency, accidental scroll, actual long-press timing) for both the v6.4 touch-placement flow and v6.6's touch-drag reposition flow; whether double-tap reliably fires `dblclick` for the port-rename shortcut on real target browsers.
- **Gesture state machines as pure, timer-free functions (v6.6 pattern, worth reusing):** when a feature needs a multi-step touch/pointer gesture (arm → wait → commit/cancel), factor the state transitions into a small object with methods the *caller* drives (e.g. `timerFire()` instead of the object owning its own `setTimeout`). This makes the whole gesture synchronously testable with plain function calls standing in for the timeline, with the real `setTimeout`/DOM wiring kept as a thin, mostly-untested shell around it. `createRepositionFSM()` (`script0.js`) is the reference example; see `test_touch_reposition.js`.
- **Sandbox/mount sync caution -- confirmed on multiple occasions across sessions, most recently in v6.6:** files in the mounted project folder can silently truncate mid-content when *edited in place*, even though the edit tool reports success. It has **also now been confirmed against a freshly-created file via the standard file-write tool**, not just in-place edits (v6.6's `test_power_circuits.js` was truncated mid-line twice, once right after being freshly authored) -- so "just create a new file instead of editing" is not itself a reliable workaround in this environment; only a full rewrite via a quoted bash heredoc (or equivalent shell-level write), followed immediately by `node -c` (syntax check, for `.js` files) and a byte-based verification (`wc -c` + `tail -c`, not `wc -l` -- truncation can land mid-line), reliably produced a byte-stable file in v6.6. Don't trust a success message alone, and don't trust a same-tool read-back either -- a prior session found the read path didn't reliably reflect true on-disk bytes.
- Rebuild pipeline: a `rebuild.py` script (recreate it in the sandbox if missing -- it's not persisted anywhere in the project folder) reassembles `build.html` from `script0-4.js` + `style.css` (main) + `rp_style.css` (RIGPOWER's shadow `:host` stylesheet, extracted via regex from `<template id="rpTpl">`). Always run this immediately after editing any extracted script/style file, before testing -- testing against a stale `build.html` has caused wasted cycles more than once.

## 9. A design decision worth understanding in full: why there's no live GDTF Share browser

This came up in an earlier session and is worth preserving in detail so it isn't silently re-litigated without new information. The user asked about pulling fixture power/DMX data from manufacturer manuals online. Investigation went:

1. GDTF Share (gdtf-share.com) has a documented REST API (login, list, download) -- but its docs are written entirely around curl/native clients, with no mention of browser CORS support, and auth relies on a PHP session cookie.
2. A standalone feasibility-test HTML file was built and the user ran it locally: the login call failed with `Failed to fetch` and no HTTP status -- consistent with the browser blocking the cross-origin credentialed request outright.
3. The user asked whether hosting the app on GitHub Pages (a real `https://` origin instead of `file://`) would fix this. It would not, and the reasoning matters: CORS is enforced by the *server* deciding which origins it trusts, not by where the *client* page happens to be hosted. Moving off `file://` doesn't change GDTF Share's server-side policy.
4. The user then asked, correctly, whether we had the integration mechanism wrong, since other software (grandMA3, Vectorworks Spotlight, the BlenderDMX addon) clearly does browse GDTF Share live. Checking BlenderDMX's actual source confirmed the real answer: it's a Python-based Blender addon making native HTTP calls -- not browser JavaScript at all. **CORS is exclusively a browser-JS sandbox restriction; it does not apply to native applications or server-to-server calls, regardless of hosting.** Every example of "live GDTF Share browsing" in the wild is a native or server-backed client, not a static browser page.
5. The only way to get a *true* live in-browser GDTF Share browser would be to add a proxy -- even a minimal one (e.g. a single serverless function) -- that the browser calls instead of gdtf-share.com directly, with the proxy (not being a browser) making the real request. This is the standard pattern for this exact problem elsewhere on the web. But it would be the app's first-ever server dependency, a real breach of the zero-network-dependency principle (§2).
6. Decision: **not worth it.** Local `.gdtf` file import already existed and already does the job (see §8) -- the user downloads the file the normal way, drops it on the Import tab, done, fully offline. If a live browser is ever revisited, it should be a deliberate, explicit decision to add a backend, not something to sneak in via "just try hosting it somewhere."

## 10. Known quirks (accepted, not bugs to silently "fix")

- The Rack Guide PDF opens via a pop-up window (print dialog -> save as PDF) -- requires allowing pop-ups for the file.
- "Paste screenshot" needs Chromium clipboard permissions; direct file Upload always works as the fallback.
- Large embedded images can approach the ~5-10 MB `localStorage` quota; the app warns once and keeps running -- Export to file is the real save at that point.
- `file://` localStorage is per-browser and per-file-path by nature of the platform, not a bug -- Export/Import is the intended cross-session/cross-file carry-forward mechanism.

## 12. Practical workflow for picking this up

1. Read `DLux Rackmaster — Project Notes.md` for full historical detail on anything summarized above.
2. Load the newest-timestamped `DLux Rackmaster *.html` in the project folder -- that's the current build.
3. Copy it into a scratch/sandbox location before editing; extract the five scripts + two stylesheets, patch there, reassemble with `rebuild.py` (recreate it if it's not present -- it's not persisted in the project folder itself).
4. Run `node test_suite_v6.10/run_all.js <path-to-new-build.html>` before touching anything, to get a clean baseline, then again after changes (note: `run_all.js`'s sequential `execFileSync` calls across the full suite can exceed some tool sandboxes' ~45s ceiling -- running each `test_*.js` file individually with an explicit path argument sidesteps this and is not itself a bug).
5. Add new test files to the existing `test_suite_v*/` folder, one per feature area, following the existing `assert()`/pass-fail-count pattern.
6. Checkpoint a new timestamped file into the project folder after each meaningful chunk of work (§6) -- live clock read immediately before saving, verified with `wc -c`/`md5sum` if it's an edit to an existing mounted file rather than a fresh one (and per §7's v6.6 update, verify freshly-created files the same way too -- this environment has now truncated both).
7. Update `DLux Rackmaster — Project Notes.md` with a new version section, and update *this* file (§8 especially) to reflect the new current state, before ending the session.
